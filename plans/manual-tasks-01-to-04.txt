TASK 1 — CREATE CLOUDFLARE R2 BUCKET AND FILL IN CREDENTIALS
Priority: CRITICAL — the entire photo upload pipeline will crash without this
────────────────────────────────────────────────────────────────────────────────

The app uses Cloudflare R2 (S3-compatible object storage) to store proof photos.
The bucket does not exist yet, and the four environment variables that the API
needs to talk to R2 are all blank in the .env file. Until this is done, any
attempt to complete a habit (which takes a photo) will throw a runtime error.

STEP 1 — Log in to Cloudflare
  Go to https://dash.cloudflare.com and sign in with your Cloudflare account.
  If you do not have an account, create one at cloudflare.com — the R2 free
  tier includes 10 GB storage and 1 million class-A operations per month, which
  is more than enough for early development and staging.

STEP 2 — Navigate to R2
  In the left sidebar, click "R2 Object Storage". If you have not used R2
  before, you may be asked to enable it for your account. Do so — it does not
  require a paid plan for the free tier.

STEP 3 — Create the bucket
  Click the "Create bucket" button in the top right.
  For the bucket name, enter exactly: rivals-proofs
  (The name must match what you will put in R2_BUCKET env var.)
  Leave the location as "Automatic" unless you have a reason to pin a region.
  Click "Create bucket".

STEP 4 — Configure CORS on the bucket
  After the bucket is created, click on it to open its settings.
  Go to the "Settings" tab inside the bucket.
  Scroll down to "CORS policy" and click "Add CORS policy".
  Add the following rule:

    Allowed origins:  * (use * for staging; restrict to your domain in prod)
    Allowed methods:  PUT, GET, HEAD
    Allowed headers:  Content-Type, Content-Length
    Max age seconds:  3600

  Save the CORS policy.
  Without this, the mobile app's direct PUT upload to R2 will be blocked by
  the browser/OS with a CORS error.

STEP 5 — Enable public access (for signed GET URLs)
  Still in the bucket Settings tab, find "R2.dev subdomain" and toggle it ON.
  Cloudflare will assign a public URL like:
    https://pub-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.r2.dev
  Copy this URL — it will become your R2_PUBLIC_BASE_URL env var.

STEP 6 — Create an API token for the bucket
  Go back to the R2 overview page (not inside a bucket).
  In the top right, click "Manage R2 API Tokens".
  Click "Create API Token".
  Give it a name like "rivals-api-staging".
  Under Permissions, select "Object Read & Write".
  Under "Specify bucket(s)", select "rivals-proofs" specifically (do not give
  it access to all buckets for security).
  Click "Create API Token".

  On the next screen, Cloudflare will show you three values ONCE. Copy all three
  immediately — you cannot view the secret again:
    - Access Key ID      (looks like a 32-char alphanumeric string)
    - Secret Access Key  (looks like a 64-char string)
    - Account ID         (shown at the top of the R2 dashboard, also a hex ID)

STEP 7 — Fill in the .env file
  Open the file: packages/api/.env
  Find the four R2 lines (currently empty) and fill them in:

    R2_ACCOUNT_ID=<the Account ID from step 6>
    R2_ACCESS_KEY_ID=<the Access Key ID from step 6>
    R2_SECRET_ACCESS_KEY=<the Secret Access Key from step 6>
    R2_PUBLIC_BASE_URL=https://pub-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.r2.dev
    R2_BUCKET=rivals-proofs

  Save the file.

STEP 8 — Add the same secrets to your Railway staging environment
  Go to your Railway project dashboard.
  Click on the API service → Variables tab.
  Add each of the five R2 variables above as environment variables.
  Railway will automatically redeploy the service after you save.

STEP 9 — Verify the connection
  After the API redeploys, hit this endpoint to confirm R2 is reachable:
    GET https://your-api-url.up.railway.app/health
  The health check should return 200. Then try completing a habit with a photo
  on the mobile app — the upload should succeed end-to-end.

TASK 2 — CREATE THE SUPABASE AVATARS STORAGE BUCKET
Priority: CRITICAL — user and group avatar uploads will silently fail without it
────────────────────────────────────────────────────────────────────────────────

The app allows users to upload a profile avatar and group admins to upload a
group icon. Both are stored in Supabase Storage in a bucket called "avatars".
This bucket must be created manually through the Supabase dashboard — it is not
created by the database migration scripts.

STEP 1 — Log in to Supabase
  Go to https://supabase.com/dashboard and sign in.
  Select your project (the one named "rivals-staging" or similar).

STEP 2 — Navigate to Storage
  In the left sidebar, click "Storage".

STEP 3 — Create the bucket
  Click "New bucket" in the top right.
  Enter the bucket name: avatars
  Toggle "Public bucket" to ON. This allows anyone to view avatar images via
  a public URL without authentication, which is correct — avatars are not
  private content.
  Click "Save".

STEP 4 — Add an RLS policy for uploads
  After creating the bucket, click on it.
  Click the "Policies" tab.
  Click "New policy" → "For full customization".
  Create a policy with these settings:
    Policy name:    allow_authenticated_upload
    Allowed operations: INSERT
    Target roles:   authenticated
    Policy definition (USING expression):
      bucket_id = 'avatars' AND auth.uid()::text = (storage.foldername(name))[1]

  This means a user can only upload to a path that starts with their own user ID,
  like: <user_id>/profile.jpg or <user_id>/group-123.jpg
  Click "Review" then "Save policy".

STEP 5 — Add a policy for updates (re-uploading an avatar)
  Click "New policy" again.
    Policy name:    allow_authenticated_update
    Allowed operations: UPDATE
    Target roles:   authenticated
    USING expression:
      bucket_id = 'avatars' AND auth.uid()::text = (storage.foldername(name))[1]
  Save it.

STEP 6 — Confirm the public read policy
  Because the bucket is public, Supabase automatically allows SELECT (read).
  Verify there is a policy for SELECT that allows "public" or "anon" role.
  If not, create one:
    Policy name:    allow_public_read
    Allowed operations: SELECT
    Target roles:   public
    USING expression: bucket_id = 'avatars'
  Save it.

STEP 7 — Note the public URL format
  In the bucket overview, Supabase shows the base URL for public files.
  It looks like:
    https://<project-id>.supabase.co/storage/v1/object/public/avatars/<path>
  This format is what the app uses to display avatar images. No additional
  configuration is needed — Supabase handles it automatically for public buckets.

TASK 4 — ENABLE pg_cron AND ACTIVATE CHALLENGE TRANSITION JOBS
Priority: CRITICAL — challenge windows will never auto-complete without this
────────────────────────────────────────────────────────────────────────────────

The app has three leaderboard modes: Streak, Total Completions, and Challenge
Window. In Challenge Window mode, an admin creates a time-bounded competition.
The system needs to automatically move windows from "upcoming" to "active" at
their start date, and from "active" to "completed" at their end date, then
declare a winner. This is handled by two pg_cron jobs defined in the file:
  packages/api/src/jobs/challenge-transitions.sql

These jobs are NOT active yet. Until they are, challenge windows are stuck in
whatever status they were created with and winners are never declared.

STEP 1 — Enable the pg_cron extension in Supabase
  Go to your Supabase project dashboard.
  Click "Database" in the left sidebar → then "Extensions".
  In the search box, type: pg_cron
  You will see "pg_cron" in the results. Click the toggle to enable it.
  Supabase will install it automatically. This may take 10–20 seconds.

STEP 2 — Open the SQL file in your code editor
  Open the file: packages/api/src/jobs/challenge-transitions.sql
  Read through it to understand the two jobs it creates:
    Job 1 (challenge-activate): runs at the top of every hour (0 * * * *)
      Finds challenge windows where start_date <= today and status = 'upcoming'
      Updates their status to 'active'
      Inserts a feed_event of kind 'window_start' for the group
    Job 2 (challenge-complete): runs at 5 minutes past every hour (5 * * * *)
      Finds challenge windows where end_date < today and status = 'active'
      Determines the winner (highest score, with tie-breaking rules)
      Updates status to 'completed', sets winner_user_id
      Awards a 'window_winner' badge to the winner
      Inserts a feed_event of kind 'window_end' for the group

STEP 3 — Run the SQL in Supabase SQL Editor
  In your Supabase project, click "SQL Editor" in the left sidebar.
  Click "New query".
  Open the file packages/api/src/jobs/challenge-transitions.sql in your editor.
  Select all the contents and copy them.
  Paste the SQL into the Supabase SQL Editor.
  Click "Run" (or press Ctrl+Enter / Cmd+Enter).
  You should see a success message — no rows affected is normal.

STEP 4 — Verify the jobs were registered
  In the SQL Editor, run this query:
    SELECT jobid, jobname, schedule, command FROM cron.job;
  You should see two rows:
    challenge-activate    0 * * * *    <the activation SQL>
    challenge-complete    5 * * * *    <the completion SQL>
  If you see them, the cron jobs are live and will run automatically.

STEP 5 — If you need to update or re-run the jobs
  If you run the SQL again and get a "job already exists" error, first delete
  the existing jobs with:
    SELECT cron.unschedule('challenge-activate');
    SELECT cron.unschedule('challenge-complete');
  Then re-run the full SQL from challenge-transitions.sql.

STEP 6 — Monitor job runs
  After an hour, you can check if the jobs have run with:
    SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 10;
  This shows the last 10 cron executions, their status, and any error messages.

TASK 5 — RUN THE LEADERBOARD BACKFILL SCRIPT
Priority: CRITICAL — must be done after deploying task 04 code to staging
────────────────────────────────────────────────────────────────────────────────

The leaderboard and streak computation system was added in task 04. Any habit
logs that users created before task 04 was deployed are not reflected in the
leaderboard_scores or streaks tables — those rows were never computed because
the code did not exist yet. Every user who logged a habit before this deploy
will appear with score = 0 on the leaderboard, even if they have a long streak.

A one-shot backfill script exists at:
  packages/api/src/scripts/backfill-leaderboard.ts

This script iterates over every (user, group) membership pair, calls the same
recomputeScores function that the live log endpoint uses, and upserts the results
into streaks and leaderboard_scores. It is safe to run multiple times (idempotent).

STEP 1 — Make sure the API code is deployed first
  This script must be run AFTER the task 04 code (leaderboard module) is live.
  If you run it before the code is deployed, nothing in the database will have
  changed and the script will still work, but the live API endpoints won't exist
  yet to serve the results.

STEP 2 — Make sure DATABASE_URL is set in your local environment
  The script connects to the database directly. Before running it, ensure your
  local shell has DATABASE_URL set to the Supabase connection string (same value
  as in packages/api/.env from Task 3).
  You can either export it in your terminal:
    export DATABASE_URL="postgresql://postgres:password@db.xxx.supabase.co:5432/postgres"
  Or the script will pick it up automatically if your .env file is correct and
  the project's dotenv loading is set up (check the package.json scripts section).

STEP 3 — Run the script from the project root
  Open your terminal in the e:\Builds\Rivals directory and run:
    pnpm --filter @rivals/api run backfill:leaderboard

  If that command doesn't exist yet, you can run it directly with ts-node:
    pnpm --filter @rivals/api exec ts-node src/scripts/backfill-leaderboard.ts

  The script will print progress as it processes each membership pair. If there
  are no users yet (fresh staging environment), it will complete immediately
  with 0 rows processed — that is fine.

STEP 4 — Verify the results
  After the script completes, open the Supabase SQL Editor and run:
    SELECT COUNT(*) FROM leaderboard_scores WHERE score > 0;
    SELECT COUNT(*) FROM streaks WHERE current_streak > 0;
  If users have logged habits, both counts should be greater than 0.
  Also open the app and check the leaderboard for a group — scores should now
  appear correctly instead of all being 0.

STEP 5 — You only need to run this once
  After the initial backfill, every new habit log triggers recomputeScores
  automatically inside the POST /logs transaction. So going forward, scores
  stay up to date in real time. This script is only for the historical data
  that existed before task 04 was deployed.

TASK 7 — ADD IMAGE PICKER TO THE CREATE GROUP SCREEN
Priority: MEDIUM — this requires a code change; current UX is a plain text input
────────────────────────────────────────────────────────────────────────────────

Right now, the CreateGroupScreen (apps/mobile/src/screens/groups/CreateGroupScreen.tsx)
has a plain text input field where the admin types or pastes an avatar URL for
the group. This is not acceptable UX for a mobile app. The correct flow is:
  1. Admin taps an avatar placeholder or camera icon
  2. Image picker opens (photo library or camera)
  3. Selected image is uploaded to Supabase Storage (avatars bucket)
  4. The returned public URL is set automatically as the group's avatarUrl

This requires writing code. Here is exactly what needs to be done:

STEP 1 — Install expo-image-picker (if not already installed)
  In your terminal at the project root, run:
    pnpm --filter @rivals/mobile add expo-image-picker
  Then rebuild the Expo dev client if you are using a development build:
    npx expo run:ios --device
    (or the Android equivalent)
  Note: expo-image-picker is part of the Expo SDK and should work without
  native rebuilds if you are using Expo Go, but if you have a custom dev
  client, a rebuild is needed.

STEP 2 — Update app.config.ts to add the photo library permission
  Open apps/mobile/app.config.ts
  Under the "ios" section, add to infoPlist:
    NSPhotoLibraryUsageDescription: "Choose a photo for your group avatar"
  Under the "android" section, add to permissions:
    "READ_MEDIA_IMAGES"
  This is required for iOS and Android to show the permission dialog.

STEP 3 — Modify CreateGroupScreen.tsx
  Open: apps/mobile/src/screens/groups/CreateGroupScreen.tsx
  Replace the plain text avatarUrl input with this flow:

  a) Add state for the local image URI:
       const [avatarUri, setAvatarUri] = useState<string | null>(null);
       const [uploading, setUploading] = useState(false);

  b) Add a function to pick and upload the image:
       async function pickAndUploadAvatar() {
         const result = await ImagePicker.launchImageLibraryAsync({
           mediaTypes: ImagePicker.MediaTypeOptions.Images,
           allowsEditing: true,
           aspect: [1, 1],
           quality: 0.8,
         });
         if (result.canceled) return;
         const uri = result.assets[0].uri;
         setAvatarUri(uri);
         setUploading(true);
         try {
           const ext = uri.split('.').pop() ?? 'jpg';
           const path = `${supabase.auth.getUser()?.data.user?.id}/group-${Date.now()}.${ext}`;
           const blob = await (await fetch(uri)).blob();
           const { error } = await supabase.storage.from('avatars').upload(path, blob, {
             contentType: `image/${ext}`,
             upsert: true,
           });
           if (error) throw error;
           const { data } = supabase.storage.from('avatars').getPublicUrl(path);
           setValue('avatarUrl', data.publicUrl);
         } catch (e) {
           Alert.alert('Upload failed', 'Could not upload avatar. Try again.');
         } finally {
           setUploading(false);
         }
       }

  c) Replace the text input in the JSX with a tappable avatar preview:
       <TouchableOpacity onPress={pickAndUploadAvatar} disabled={uploading}>
         {avatarUri ? (
           <Image source={{ uri: avatarUri }} style={styles.avatarPreview} />
         ) : (
           <View style={styles.avatarPlaceholder}>
             <Text style={styles.avatarPlaceholderText}>
               {uploading ? 'Uploading...' : 'Tap to add group photo'}
             </Text>
           </View>
         )}
       </TouchableOpacity>

  d) Add the necessary styles to the StyleSheet at the bottom of the file:
       avatarPreview: { width: 100, height: 100, borderRadius: 50 },
       avatarPlaceholder: {
         width: 100, height: 100, borderRadius: 50,
         backgroundColor: '#1e2a3a', alignItems: 'center',
         justifyContent: 'center', borderWidth: 1, borderColor: '#f59e0b',
       },
       avatarPlaceholderText: { color: '#f59e0b', fontSize: 12, textAlign: 'center' },

STEP 4 — Test the flow
  Run the app on a simulator or real device.
  Navigate to Groups → Create Group.
  Tap the avatar placeholder → image picker should open.
  Select a photo → it should upload and show a preview thumbnail.
  Fill in the group name and tap Create → the group should be created with

TASK 12 — CONFIRM GOOGLE OAUTH REDIRECT URL IN SUPABASE (OPTIONAL)
Priority: LOW — only needed if users are signing in with Google
────────────────────────────────────────────────────────────────────────────────

Task 01.5 requires Google OAuth login as an option. For this to work in the
mobile app, the `rivals://auth/callback` deep link must be registered as an
allowed redirect URL in Supabase's Auth settings.

STEP 1 — Go to Supabase Auth settings
  Supabase Dashboard → Authentication → URL Configuration.

STEP 2 — Add the redirect URL
  Under "Redirect URLs", click "Add URL".
  Add: rivals://auth/callback
  Click "Save".
  Also add the web equivalent if you have a domain:
    https://yourdomain.com/auth/callback

STEP 3 — Configure Google OAuth credentials
  Still in Authentication, click "Providers" in the sidebar.
  Click "Google".
  Toggle it ON.
  You will need a Google OAuth Client ID and Client Secret.
  To get them:
    a) Go to https://console.cloud.google.com
    b) Create or select a project
    c) Navigate to "APIs & Services" → "Credentials"
    d) Click "Create Credentials" → "OAuth 2.0 Client IDs"
    e) Application type: "Web application" (Supabase uses this even for mobile)
    f) Under "Authorized redirect URIs", add your Supabase callback URL:
         https://<your-project-id>.supabase.co/auth/v1/callback
    g) Copy the Client ID and Client Secret
  Paste them into the Supabase Google provider settings.
  Click "Save".

STEP 4 — Test the Google login flow
  On the mobile app, tap "Continue with Google" on the LoginScreen.
  A browser window should open showing Google's login page.
  After logging in, it should redirect back to the app via the rivals:// deep link.
  The app should detect the session and navigate to the Dashboard.
  If the redirect does not work, double-check that rivals://auth/callback is in
  both Supabase's redirect URL list and the app.config.ts scheme configuration.

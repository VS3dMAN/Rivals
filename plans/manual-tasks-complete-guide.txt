TASK A1 — Create R2 bucket "rivals-proofs"

Context:
  The Rivals app lets users upload proof photos of habit completions.
  These photos are stored in Cloudflare R2 (S3-compatible object storage).
  The bucket and API token do not exist yet.

Prerequisites:
  - Cloudflare account with R2 enabled (free tier is fine)
  - Access to fill .env files

Step 1: Create the bucket
  Go to https://dash.cloudflare.com → R2 Object Storage → "Create bucket"
  Bucket name: rivals-proofs (exact match)
  Location: Automatic
  Click "Create"
  Wait for creation (< 1 min).

Step 2: Configure CORS
  Click the "rivals-proofs" bucket → Settings tab
  Scroll to "CORS policy" → "Add CORS policy"
  Fill:
    Allowed origins: *
    Allowed methods: PUT, GET, HEAD
    Allowed headers: Content-Type, Content-Length
    Max age: 3600
  Click "Save"

Step 3: Enable public read (R2.dev subdomain)
  Still in Settings, find "R2.dev subdomain"
  Toggle it ON
  Cloudflare assigns a URL like: https://pub-abc123...r2.dev
  COPY this URL — it becomes R2_PUBLIC_BASE_URL

Step 4: Create API token
  Leave the bucket settings page.
  Go back to R2 overview (main R2 page).
  Top right: "Manage R2 API Tokens"
  "Create API Token"
  Name: rivals-api-staging
  Permissions: "Object Read & Write"
  Bucket restrictions: Select "rivals-proofs" (not "All buckets")
  Click "Create API Token"
  Cloudflare shows 3 values ONCE — copy all:
    - Access Key ID
    - Secret Access Key
    - Account ID (shown at top of R2 dashboard, also in URL)

Step 5: Fill .env locally
  Open packages/api/.env
  Find the R2 section (look for R2_ACCOUNT_ID)
  Fill:
    R2_ACCOUNT_ID=<Account ID from step 4>
    R2_ACCESS_KEY_ID=<Access Key ID>
    R2_SECRET_ACCESS_KEY=<Secret Access Key>
    R2_PUBLIC_BASE_URL=https://pub-...r2.dev
    R2_BUCKET=rivals-proofs
  Save the file.

Step 6: Add to Render environment
  Go to https://render.com → Dashboard → select your API service
  Go to Environment → Environment variables
  Add each of the 5 variables above (R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, etc.).
  Render redeploys automatically when you add variables.
  Wait for the deploy to complete (status shows "Live").

Step 7: Verify
  Once Render shows "Live":
  curl https://your-api-url.onrender.com/health
  Should return 200.
  In the Rivals app, complete a habit with a photo.
  Upload should succeed end-to-end.

Troubleshooting:
  - CORS error on photo PUT: re-check CORS policy in R2 bucket settings
  - "Access Denied" on token: re-check API token has "rivals-proofs" selected
  - R2_PUBLIC_BASE_URL 404: confirm subdomain toggle was ON

TASK A2 — Create Supabase "avatars" bucket
================================================================================

Context:
  Users and group admins can upload avatar images (profile pics, group icons).
  Stored in Supabase Storage, which has built-in RLS.

Prerequisites:
  - Supabase project (rivals-staging or similar)
  - Access to Supabase dashboard

Step 1: Navigate to Storage
  Go to https://supabase.com/dashboard → select your project
  Left sidebar: "Storage"

Step 2: Create bucket
  "New bucket"
  Name: avatars (exact)
  Toggle "Public bucket" to ON (anyone can read, RLS controls write)
  Click "Save"
  Wait a few seconds.

Step 3: Create upload policy (authenticated users only)
  Click the "avatars" bucket
  "Policies" tab
  "New policy" → "For full customization"
  Fill:
    Policy name: allow_authenticated_upload
    Allowed operations: INSERT
    Target roles: authenticated
    USING expression: bucket_id = 'avatars' AND auth.uid()::text = (storage.foldername(name))[1]
  This means a user can only write to a folder named after their user ID.
  Click "Review" → "Save policy"

Step 4: Create update policy (for re-uploads)
  "New policy" again
  Policy name: allow_authenticated_update
  Allowed operations: UPDATE
  Target roles: authenticated
  USING: bucket_id = 'avatars' AND auth.uid()::text = (storage.foldername(name))[1]
  Save.

Step 5: Verify public read policy
  Because the bucket is "Public", SELECT is auto-allowed for public/anon.
  Verify there is a policy that says "public" role, "SELECT" operation.
  If missing, create one:
    Policy name: allow_public_read
    Allowed operations: SELECT
    Target roles: public
    USING: bucket_id = 'avatars'

Step 6: Test
  In the app, go to Profile → edit avatar, or Group Settings → edit group avatar.
  Tap the placeholder and pick a photo.
  Upload should succeed.
  Avatar should appear immediately.

Troubleshooting:
  - 403 on upload: check RLS policy — confirm auth.uid() matches the folder name
  - Avatar not visible: confirm public read policy exists

TASK A4 — Enable pg_cron and run challenge jobs
================================================================================

Context:
  The app has cron jobs that automatically transition challenge windows
  (upcoming → active → completed) and send "window ending soon" notifications.
  These are SQL-based jobs that run on the Supabase database itself.

Prerequisites:
  - Supabase project
  - Access to SQL Editor

Step 1: Enable pg_cron extension
  Supabase dashboard → Database → Extensions
  Search for "pg_cron"
  Toggle to enable.
  Wait 10–20 seconds.

Step 2: Run challenge-transitions job
  Supabase → SQL Editor → "New query"
  Open the file packages/api/src/jobs/challenge-transitions.sql
  Copy ALL the SQL.
  Paste into the SQL Editor.
  Click "Run" (or Ctrl+Enter).
  You should see "Query executed successfully" (no rows affected is normal).

Step 3: Run challenge-ending-soon job
  Supabase → SQL Editor → "New query"
  Open packages/api/src/jobs/challenge-ending-soon.sql
  Copy ALL the SQL.
  Paste and Run.
  Expect success.

Step 4: Verify jobs are registered
  SQL Editor → "New query"
  Paste:
    SELECT jobid, jobname, schedule, command FROM cron.job;
  Run.
  You should see rows for:
    - challenge-activate (schedule: 0 * * * *)
    - challenge-complete (schedule: 5 * * * *)
    - challenge-ending-soon (schedule: 10 * * * *)
  If any are missing, re-run their SQL from steps 2–3.

Step 5: Monitor execution
  After an hour, check:
    SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 10;
  You should see successful runs.
  If errors, the "command" and "message" columns will show why.

Troubleshooting:
  - "job already exists": run these first to unschedule:
      SELECT cron.unschedule('challenge-activate');
      SELECT cron.unschedule('challenge-complete');
      SELECT cron.unschedule('challenge-ending-soon');
    Then re-run the SQL from steps 2–3.
  - pg_cron not found: confirm extension was enabled in step 1

TASK A5 — Run leaderboard backfill script
================================================================================

Context:
  Task 04 (leaderboard engine) was implemented weeks ago, but any habit logs
  from BEFORE that deploy are missing from the leaderboard_scores table.
  This script retroactively computes scores for all existing (user, group) pairs.

Prerequisites:
  - API code (task 04 or later) is deployed to Render
  - DATABASE_URL is set locally (from A3 above)
  - You have git access to Rivals repo

Step 1: Confirm task 04 is deployed
  Go to Render → Dashboard → select your API service → Deployments
  Confirm a recent deployment is "Live" (green status).

Step 2: Set DATABASE_URL locally
  Open your shell (terminal / PowerShell).
  Set the environment variable:
    Bash: export DATABASE_URL="postgresql://postgres:xxx@db.yyy.supabase.co:5432/postgres"
    PowerShell: $env:DATABASE_URL = "postgresql://postgres:xxx@db.yyy.supabase.co:5432/postgres"
  (Same value as packages/api/.env)

Step 3: Run the script
  From the project root (e:\Builds\Rivals):
    pnpm --filter @rivals/api run backfill:leaderboard
  Or if that command doesn't exist:
    pnpm --filter @rivals/api exec ts-node src/scripts/backfill-leaderboard.ts
  The script will print progress lines like:
    "Processing (user: abc, group: def)..."
  When it finishes, you will see:
    "Backfill complete. X rows processed."

Step 4: Verify the results
  Open Supabase SQL Editor.
  Run:
    SELECT COUNT(*) FROM leaderboard_scores WHERE score > 0;
    SELECT COUNT(*) FROM streaks WHERE current_streak > 0;
  Both counts should be > 0 if your staging environment has logs.
  Open the Rivals app and check the Leaderboard for a group — scores should appear.

Troubleshooting:
  - "No such file": confirm packages/api/src/scripts/backfill-leaderboard.ts exists
  - "Permission denied": re-check DATABASE_URL is set in your shell
  - "Connection timeout": confirm the URL is reachable and password is correct

TASK A7 — Set up Uptime Robot (keep Render alive)
================================================================================

Context:
  Render's free tier spins down after 15 minutes of inactivity.
  Uptime Robot is a free service that pings your API every 5 minutes,
  keeping it awake 24/7. Without this, the first user request after
  inactivity will experience a 60-120 second cold start.

Prerequisites:
  - Uptime Robot account (free, no credit card required)
  - Render API URL (from previous tasks)

Step 1: Create Uptime Robot account
  Go to https://uptimerobot.com
  "Sign up" → email + password
  Verify your email (link sent to inbox)

Step 2: Create a monitor
  Uptime Robot Dashboard → "Add New Monitor"
  Fill:
    Monitor Type: HTTP(s)
    Monitor Friendly Name: "Rivals API Keep-Alive"
    URL: https://your-api.onrender.com/health
    Monitoring Interval: 5 minutes
    (5-minute interval is perfect for keeping Render alive — requires the service
     to respond every 15 minutes, and Uptime Robot pings every 5 min.)
  Click "Create Monitor"

Step 3: Verify the monitor is working
  Uptime Robot Dashboard should show:
    Status: Up (green checkmark)
    Last Checked: just now
  If "Down" or "Pending", wait a few seconds and refresh.
  If it stays "Down", double-check the API URL is correct.

Step 4: (Optional) Set up Slack alert
  If you want to be notified if the API ever goes down:
    Uptime Robot → Settings → Alert Contacts
    "Add" → Slack
    Authorize Uptime Robot in Slack
    Choose a Slack channel (#rivals-oncall)
    In your monitor, check "Send notifications to: Slack"

Step 5: Confirm the setup
  Your API is now continuously pinged by Uptime Robot every 5 minutes.
  This keeps it awake on Render's free tier.
  Real user requests will get instant responses (no cold starts, as long as
  the Uptime Robot pings keep the service warm).

Troubleshooting:
  - Monitor shows "Down": confirm API is running (Render → Logs), and URL is correct
  - Not receiving Slack alerts: re-check Slack workspace authorization
  - API still slow: if response time > 60 sec, it may be a cold start happening before Uptime Robot pings it
    (e.g., if your app is idle for more than 15 mins, first user hits a cold start, then Uptime Robot
     keeps it warm afterward). This is acceptable per your requirements.

TASK A8 — Set up Firebase Web Push
================================================================================

Context:
  Web push (Chrome, Safari, Firefox) is delivered via Firebase Cloud Messaging (FCM).
  You need a Firebase project, a Web Push VAPID key pair, and credentials in the API.

Prerequisites:
  - Google Cloud account
  - Firebase access

Step 1: Create a Firebase project (or use existing)
  Go to https://console.firebase.google.com
  "Create a project" or select existing.
  Name: rivals (or rivals-staging).
  If creating, enable Google Analytics (recommended).

Step 2: Enable Cloud Messaging
  In your Firebase project → Settings → Cloud Messaging tab
  You should see a "Server API key" (legacy) and "Sender ID".
  Under "Web Push certificates", if empty, click "Generate key pair".
  This generates a VAPID key pair. Copy both:
    - VAPID public key → EXPO_PUBLIC_FIREBASE_VAPID_KEY
    - VAPID private key → save for later (Firebase config step)

Step 3: Get Firebase Web config
  In Firebase → Settings → General tab
  Scroll down to "Your apps" section.
  If no web app yet, click "Add app" → "Web".
  Register app as "rivals-web".
  Firebase shows:
    {
      apiKey: "...",
      authDomain: "...",
      projectId: "...",
      storageBucket: "...",
      messagingSenderId: "...",
      appId: "..."
    }
  Copy this config object.

Step 4: Fill app.config.ts
  Open apps/mobile/app.config.ts (or wherever Expo config is sourced).
  Add to the "extra" section:
    extra: {
      ...,
      firebaseApiKey: process.env.EXPO_PUBLIC_FIREBASE_API_KEY,
      firebaseAuthDomain: process.env.EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN,
      firebaseProjectId: process.env.EXPO_PUBLIC_FIREBASE_PROJECT_ID,
      firebaseStorageBucket: process.env.EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET,
      firebaseMessagingSenderId: process.env.EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID,
      firebaseAppId: process.env.EXPO_PUBLIC_FIREBASE_APP_ID,
      firebaseVapidKey: process.env.EXPO_PUBLIC_FIREBASE_VAPID_PUBLIC_KEY,
    }

Step 5: Generate server credentials (FCM HTTP v1)
  In Firebase → Settings → Service Accounts
  "Generate new private key".
  Downloads a JSON file with the full service account (includes private_key, client_email, etc.).
  KEEP THIS SAFE — do not commit it.
  Copy the entire JSON object.

Step 6: Fill API .env
  Open packages/api/.env
  Add:
    FIREBASE_SERVICE_ACCOUNT_JSON=<paste the entire JSON object from step 5>
  (Or set it as a Render environment variable if you prefer not to paste in .env.)

Step 7: Build the service worker config
  The web app's service worker (apps/mobile/public/firebase-messaging-sw.js)
  reads Firebase config from /firebase-config.js.
  This file is generated at build/deploy time from environment variables.
  Make sure your deployment pipeline does:
    cat > apps/mobile/public/firebase-config.js << EOF
    window.firebaseConfig = {
      apiKey: "$EXPO_PUBLIC_FIREBASE_API_KEY",
      authDomain: "$EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN",
      projectId: "$EXPO_PUBLIC_FIREBASE_PROJECT_ID",
      storageBucket: "$EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET",
      messagingSenderId: "$EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID",
      appId: "$EXPO_PUBLIC_FIREBASE_APP_ID"
    };
    EOF
  (Cloudflare Pages build script or GitHub Actions should do this.)

Step 8: Add env vars to Render (API) and GitHub Secrets (mobile build)
  Render → API service → Environment → Environment variables:
    FIREBASE_SERVICE_ACCOUNT_JSON=<the JSON>
  GitHub Secrets (for mobile build):
    EXPO_PUBLIC_FIREBASE_API_KEY=...
    EXPO_PUBLIC_FIREBASE_AUTH_DOMAIN=...
    EXPO_PUBLIC_FIREBASE_PROJECT_ID=...
    EXPO_PUBLIC_FIREBASE_STORAGE_BUCKET=...
    EXPO_PUBLIC_FIREBASE_MESSAGING_SENDER_ID=...
    EXPO_PUBLIC_FIREBASE_APP_ID=...
    EXPO_PUBLIC_FIREBASE_VAPID_PUBLIC_KEY=...

Step 9: Test registration
  Deploy the mobile app to the web (EAS web build or local pnpm build).
  Open in Chrome.
  You should be prompted for notification permission.
  Grant it.
  Check browser console for [push-web] "Registered token".
  Check Supabase push_tokens table — a new row with platform='web' should appear.

Step 10: Send a test notification
  Via the API (if admin endpoint exists):
    POST /admin/push/test { token: "...", title: "Test" }
  Or manually via Firebase Console → Cloud Messaging → Send your first message.
  Confirm notification arrives on the Chrome tab.

Troubleshooting:
  - Firebase init fails: check apiKey and projectId are correct
  - Service worker fails to load: confirm /firebase-config.js is generated and deployed
  - "onBackgroundMessage not fired": check sw.js event listener is registered
  - Token registration 401: confirm EXPO_PUBLIC_SUPABASE_ANON_KEY is correct

TASK A10 — Set up Sentry alert rules
================================================================================

Context:
  Sentry monitors errors in production (mobile + API).
  Alert rules define which errors trigger notifications (Slack, PagerDuty, email).

Prerequisites:
  - Sentry account with rivals-mobile and rivals-api projects already created
  - Slack workspace (optional but recommended)
  - PagerDuty account (optional but recommended for on-call)

Step 1: Open Sentry projects
  Go to https://sentry.io → Organizations → Rivals
  You should see two projects:
    - rivals-api
    - rivals-mobile

Step 2: Integrate Slack (optional but recommended)
  Sentry → Settings → Integrations → Slack
  "Install Slack" → authorize Sentry to your Slack workspace
  Select which channels to notify (e.g., #rivals-oncall, #rivals-mobile)

Step 3: Integrate PagerDuty (optional, for on-call)
  Sentry → Settings → Integrations → PagerDuty
  Authorize with your PagerDuty account
  Select which PagerDuty services to trigger (e.g., Rivals primary)

Step 4: Apply alert rules (rivals-api)
  Go to rivals-api project → Alerts
  For each rule in infra/sentry/alert-rules.yml that starts with "API —":
    "Create Alert Rule" → fill the details:
      - Name: "error rate spike" (or the rule name)
      - Condition: "failure_rate > 0.02" (or as specified in YAML)
      - Action: "Notify Slack" → select #rivals-oncall
      - Action: "Notify PagerDuty" → select service
    Click "Save Rule"
  Repeat for other API rules (unhandled exception, proof-upload failures, etc.)

Step 5: Apply alert rules (rivals-mobile)
  Go to rivals-mobile project → Alerts
  Apply similar rules, but for mobile:
    - "crash-free sessions below SLO" → notify #rivals-mobile
    - "new release regression" → notify #rivals-mobile
    - "first-seen issue in latest release" → notify #rivals-mobile

TASK A15 — Capture EXPLAIN ANALYZE queries
================================================================================

Context:
  The leaderboard is a complex query involving joins across multiple tables.
  EXPLAIN ANALYZE shows the query plan and actual execution time.
  This helps identify missing indexes or inefficient queries.

Prerequisites:
  - DATABASE_URL set locally
  - packages/api/src/scripts/explain-leaderboard.ts exists
  - Staging database populated with at least 50k habit logs

Step 1: Run the explain script
  From the project root:
    DATABASE_URL=postgres://... \
      pnpm --filter @rivals/api exec ts-node src/scripts/explain-leaderboard.ts
  The script runs 4 EXPLAIN ANALYZE queries and prints the plans.

Step 2: Capture the output
  The script outputs JSON or text like:
    EXPLAIN ANALYZE for leaderboard top 50:
    Seq Scan on leaderboard_scores ... (cost=0.00..1234.56 rows=50)
    Execution Time: 15.234 ms
  Copy all 4 plans to a text file.

Step 3: Identify slow queries
  Look for these warning signs:
    - Seq Scan (full table scan) — should be Index Scan
    - cost > 10000 — might be missing index
    - Execution Time > target (e.g., > 30 ms for leaderboard query)

Step 4: Check for missing indexes
  In Supabase SQL Editor, run:
    SELECT * FROM pg_indexes WHERE schemaname = 'public';
  Compare against the 8 required indexes listed in perf-report.md.
  If any are missing, create a migration.

Step 5: Create a migration for missing indexes
  In packages/api/src/db/migrations/, create a new migration:
    0007_add_missing_indexes.sql
  Example:
    CREATE INDEX IF NOT EXISTS ix_habit_logs_user_group_date
    ON habit_logs(user_id, group_id, log_date);
  Apply the migration to staging via Supabase SQL Editor.

Step 6: Rerun the explain script
  After indexes are added, rerun step 1.
  Verify that queries now use Index Scan and execution time improves.

Step 7: Paste results into perf-report.md
  Open Vibe Code/perf-report.md → "Query plans" section.
  Under each query (Leaderboard, Feed, Streak, Notifications), paste:
    - The EXPLAIN ANALYZE output
    - The execution time
  Mark green if execution time < target, red if over.

Troubleshooting:
  - "EXPLAIN: no such index": the index doesn't exist yet; create the migration first
  - Script timeout: the database is busy or the query is genuinely slow; try again later
  - Seq Scan still present: the index may not have been created; check with SELECT * FROM pg_indexes
